## 목표

원본을 저장하고 영속 분석 작업을 만들며 파일별 성공·실패를 보여준다.

## 출발 상태

로컬 저장·다중 업로드 검증됨; S3 실연동 미검증. 이 상태는 계획 작성 시점의 기준이며 이번 작업의 완료 증거가 아니다. 기존 구현과 테스트를 읽고 부족한 부분만 변경한다.

## 확인할 파일

- `backend/app/storage.py`
- `backend/app/worker.py`
- `frontend/src/Upload.tsx`
- `backend/app/routers/photos.py`
- `backend/app/photo_operations.py`
- `backend/app/routers/analysis.py`

## 연결 계약

- `POST /api/albums/{album_id}/photos`
- `GET /api/albums/{album_id}/analysis-status`

요청·오류는 `contracts/openapi.json`, 상세 응답 의미는 `docs/API_CONTRACT.md`, Python 호출 경계는 `contracts/python-interfaces.json`을 따른다. 응답 타입 자동 생성은 아직 없으므로 프론트 타입과 실제 응답도 함께 확인한다.

## 진행 순서

1. `git status`와 선행 PR을 확인하고 M 번호가 있는 작업 브랜치를 사용한다.
2. 현재 기능을 재현하고 완료 조건별로 구현됨/부족함/외부 검증 필요를 나눈다.
3. 주관 범위의 변경을 구현한다. 공유 API·DB·화면 변경은 통합 담당과 조정한다.
4. 아래 검사를 실행하고 정상·실패 경로를 확인한다. 외부 검증은 샘플로 대체하지 않는다.
5. 기능 단위 커밋과 PR에 계약 변경·검사 결과·남은 조건을 기록한다.
