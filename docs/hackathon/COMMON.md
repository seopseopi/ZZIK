# 공통 작업 프롬프트

아래 지시와 자신의 역할/M 작업 프롬프트를 함께 사용한다.

> 찍 / ZZIK은 여행 사진을 인물별로 분류하고, 선택·보정·버전·승인·다운로드까지 연결하는 서비스다. 현재 저장소의 완성된 기능을 먼저 읽고 재현한 다음, 지정된 작업의 부족한 부분을 구현하라. 기존 기능을 삭제하고 처음부터 만들지 마라.
>
> `AGENTS.md`, `docs/hackathon/OWNERSHIP.md`, `docs/hackathon/SCOPE.md`, `docs/API_CONTRACT.md`, `contracts/README.md`를 읽어라. 먼저 변경할 파일과 완료 조건을 정리하고 선행 작업·공유 계약을 확인하라. 이번 M 작업 범위 안에서 구현·검증·커밋·PR까지 단계별로 진행하라.
>
> 화면 이름은 찍이다. 기존 데스크톱 블루·모바일 코랄 디자인과 간결한 화면을 유지하라. 서비스 화면에 개발용 설명이나 불필요한 문구를 추가하지 마라. 원본 사진을 변경하지 말고, 승인 대상은 확인된 등장 멤버 전원이라는 정책을 보존하라.
>
> 브라우저 체험·fixture·모의 AWS 응답·실제 AWS 결과를 구분하라. 미구현·실패·미확정 정보를 성공처럼 표시하지 마라. 새 계약·DB 변경은 통합 담당과 조정하고 프론트/테스트/문서를 함께 갱신하라.
>
> 필요한 검사만 실행하고, 완료 보고에는 변경 동작, 실행 결과, 외부 검증이 남은 조건을 적어라. 과거 초기 커밋을 팀원별 개발 이력으로 재작성하지 마라. 실제 작업 기록을 기능 단위 PR로 남겨라.

첫 작업 예: 4번 역할 프롬프트와 M03 프롬프트를 제공하며 “공통 규칙에 따라 M03의 실제 기준 얼굴 등록 검증을 진행해 줘”라고 지시한다. 전체 M 목록을 매번 구현하라는 지시로 사용하지 않는다.

## 조립 연습의 PR 자동 판단

[PR 운영 규칙](PR_WORKFLOW.md)을 함께 읽는다. Kiro가 작업 단위와 PR 시점을 판단하며 선행 기능이 없거나 검사가 막히면 Draft와 의존성을 남긴다. 사람 리뷰·병합은 통합 담당에게 인계한다.
