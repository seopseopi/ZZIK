# Kiro 자율 조립·Git 운영 규칙

사용자 요청에 따라 이전의 매 단계 사람 리뷰/병합 대기 규칙을 대체한다. **설정된 역할의 Kiro가 구현·검사·커밋·PR·교차 검토·후보 통합·최종 병합까지 진행한다.** 단, 주최 측 저장소의 실제 권한·필수 리뷰·필수 검사는 우회하지 않는다. GitHub이 사람의 승인을 요구하면 그 외부 조건만 요청한다. 일상적인 작업 순서나 커밋 시점을 사람에게 되묻지 않는다.

이 문서는 실행 지침이다. Kiro 세션을 자동 기동하거나 다른 세션에 작업을 전달하는 데몬이 설치된 것은 아니다. 각 팀원은 자기 계정으로 Kiro 세션을 시작하고 실행 권한을 연결한다. 세션이 종료되면 아래 동일 프롬프트로 이어간다. 실제 Kiro 5세션 자율 조립은 아직 미검증이다.

## 시작 전에 한 번 입력할 사실

대회 저장소를 받으면 **그 저장소를 clone**한다. `seopseopi/ZZIK`은 준비용이며 제출 저장소로 고정하지 않는다. 기존 공식 README/규정/이력은 보존하고 origin 변경·force push·저장소 재생성을 하지 않는다. 사전 코드·프롬프트 반입이 허용된 범위 안에서 starter를 도입한다. 불허하면 완성 코드나 starter를 옮기지 않고 허용된 명세만 이용하도록 계획을 다시 정한다.

`starter/team.example.json`을 `.zzik-assembly.json`으로 복사해 다음 사실만 입력한다. 비밀번호·토큰은 넣지 않는다. 이 비밀정보 없는 설정은 팀이 공유하도록 커밋한다.

- `repository`: 실제 `OWNER/REPO` (URL 아님).
- `base_branch`: 주최 측이 정한 제출/통합 브랜치. 연습은 `starter/local-v1`, 대회는 제공 브랜치를 사용한다.
- `mode`: `rehearsal` 또는 `contest`, `run_id`: 연습/대회 실행 식별자.
- `roles`: 1~5번 실제 GitHub 로그인 이름.
- `starter_import_allowed`, `rules_reference`: 반입 허용 확인과 공지/운영진 답변 근거. 대회 규정 미확인을 허용으로 채우지 않는다. 연습 저장소에서는 소유자의 연습 허가를 기록한다.

1번 Kiro가 공식 저장소의 기존 내용과 충돌하지 않게 허용된 공통 시작 파일·설정을 bootstrap PR로 도입한다. 3번 Kiro가 diff·규정 범위·기존 이력 보존을 검토한 뒤 저장소 정책에 맞춰 병합한다. 구성 파일의 base가 원격에 존재해야 팀 작업을 시작한다. 이 한 번의 준비 전에 별도 대회 레포를 만들지 않는다.

```sh
python3 scripts/assembly_plan.py plan
python3 scripts/assembly_plan.py preflight --role 3
```

`plan`은 입력·역할별 단위/브랜치/검토자/순서를 결정하며, `preflight`는 origin·로그인·push 권한·원격 base·작업 트리를 조회한다. 스크립트 자체가 코드를 구현하거나 PR을 병합하지는 않는다. Kiro가 출력과 아래 규칙을 실행한다. 원본 개발용 누적 PR의 base는 기존 의존 브랜치를 유지한다.

## 사람이 정할 필요 없이 고정하는 운영 방식

| 항목 | 고정 규칙 |
|---|---|
| 동시 작업 | 5개 역할이 각자 checkout과 계정으로 진행. 같은 작업 디렉터리를 공유하지 않음 |
| 역할 브랜치 | `work/<run_id>/role-1`~`role-5`, 역할별 계속 사용 |
| 역할 PR | 역할당 1개 Draft PR을 일찍 만들고 변경/검사/의존성을 계속 갱신. base는 설정값 |
| 구현 순서 | `assembly_plan.py plan`의 자기 `units_in_order`. 막힌 단위는 필요한 함수·역할을 기록하고 다음 독립 단위로 이동 |
| 커밋 시점 | 의미 있는 구현 단위와 해당 검증이 끝날 때. 30개 단위는 작업 분할 기준이며 커밋 할당량이 아님 |
| 교차 검토 | 1번 PR→3번 Kiro, 2번→5번, 3번→1번, 4번→3번, 5번→2번 |
| 후보 통합 | 3번 Kiro만 `assemble/<run_id>`에 1→3→4→5→2 순서로 실제 역할 커밋을 merge |
| 최종 검토 | 1번 Kiro가 후보 통합 diff·전체 검사·각 역할 검토를 확인 |
| 최종 PR/병합 | 후보→설정된 base로 통합 PR 1개. 필요한 검사·리뷰 통과 후 3번 Kiro가 허용된 merge 방식으로 반영 |
| 병합 방식 | 기본 merge commit으로 실제 기능 커밋 보존. 주최 측이 squash만 허용하면 그 정책을 따르며 PR 내 커밋/검사 기록 보존 |
| AWS | 준비만. 새 자원 생성·서버 중단은 이번 자율 조립 범위 밖 |

역할 PR은 검토와 변경 추적용이다. **미완성 역할 PR의 빨간 acceptance를 무시하고 제출 브랜치에 병합하지 않는다.** 후보 브랜치에서 먼저 합쳐 전체 검사를 통과시킨다. 최종 통합 PR이 병합되면 역할 PR은 포함된 커밋과 통합 PR 링크를 남기고 닫는다. 개별 PR이 GitHub에서 merge되지 않았다면 merged라고 보고하지 않는다. 후보에 선행 작업을 담는 것과 제출 브랜치 완료를 구분한다.

## 각 역할 Kiro의 실행 루프

1. 시작/재개 시 설정, 실제 gh 로그인, origin, git status, 원격 브랜치·열린 PR을 확인한다. 기존 실행 브랜치와 PR을 재사용해 중복 생성을 피한다.
2. 자기 단위 중 진행 가능한 첫 작업을 구현한다. 공통 기반·API/DB 계약·다른 역할 함수·기존 테스트를 임의로 바꾸지 않는다. 계약 변경은 원인·영향을 PR에 기록하고 담당 Kiro가 검토한다.
3. `starter.py status`로 해당 단위, missing/protected 변경을 확인한다. 단위별 정상/실패 동작 검사와 harness, 영향받는 타입/빌드를 실행한다. 관련 기존 테스트를 선택하면 정확한 테스트 ID·이유·결과를 남긴다. 검사가 없으면 의미 있는 테스트를 추가한다.
4. 통과한 구현 단위를 실제 변경 내용의 메시지로 커밋하고 push한다. 검사 차단은 완료로 표시하지 않는다. 필요한 협업을 보여주는 미완성 checkpoint는 `wip:`로 명시하고 실패/미실행 검사를 PR에 기록한다. 자동으로 타인 변경을 커밋하지 않는다.
5. 역할 PR 본문에 단위별 상태, 정확한 head SHA, 변경 함수, 검사 명령/결과, 차단 의존성을 갱신한다. 모든 자기 단위와 가능한 검사가 끝나면 검토 요청 상태로 전환한다. 다른 역할 미구현으로 전체 검사가 실패하면 정확한 실패 원인을 남기고 후보 통합에서 재검증한다.
6. 자신에게 배정된 다른 역할 PR이 준비됐으면 아래 교차 검토를 수행한다. 피드백을 받은 작성 Kiro는 수정·검사·추가 커밋 후 재검토를 요청한다. 필요 없는 커밋 분할이나 동일 변경 반복은 하지 않는다.
7. 원격 의존 PR과 후보 진행을 주기적으로 조회한다. 새로운 이벤트가 없으면 짧은 간격의 무한 조회를 하지 말고 30~60초 간격으로 기다린다. 세션 한도/인증/권한/사람만 답할 수 있는 규정이 막히면 상태를 저장하고 그 조건만 보고한다. 새 사용자 입력은 즉시 반영한다.

각 Kiro는 다른 계정 세션을 대신 실행했다고 주장하지 않는다. 새 세션은 Git·열린 PR의 최신 상태에서 재개한다. 지속적인 백그라운드 감시가 필요하면 별도 실행 서비스가 필요하며 현재 제공 범위가 아니다.

## 교차 검토: 실제 기록을 남긴다

검토자 역할의 Kiro가 **자기 팀원 계정**에서 PR diff와 실제 head SHA를 읽고 관련 검사를 확인/실행한다. 기능·오류 처리·권한·원본 보존·승인 규칙·역할 범위·검사 누락을 검토한다. AI가 작성한 검토임을 명시한다. 다른 팀원으로 author를 꾸미거나 계정/토큰을 공유하지 않는다.

```text
[AI-assisted review]
검토한 PR/head SHA:
검토한 파일·동작:
실행/확인한 검사와 결과:
발견 사항: 파일·위치·재현·수정 요구 (없으면 발견 없음)
판정: changes requested / 역할 범위 통과 / 후보 통합 후 재검증 필요
남은 의존성과 한계:
```

실제 검토 후 권한과 규정이 허용하면 `gh pr review`로 기록한다. 아직 통합 검사가 안 된 상태를 전체 서비스 승인으로 쓰지 않는다. 같은 계정의 자기 PR은 승인하지 않으며 연습에서 같은 계정을 재사용했다면 독립 팀원 리뷰가 아님을 명시한다. head가 바뀌면 이전 검토가 최신 코드를 검토한 것으로 간주하지 않는다. 최종 PR에 새 커밋이 생기면 검토와 영향 검사도 갱신한다.

## 3번 Kiro의 후보 통합과 최종 병합

- 작업 시작 시 확보한 base 커밋을 기록한다. 각 역할 PR의 head SHA와 검토 상태를 고정해 후보에 merge한다. 한 checkout의 전체 파일 복사나 완성본 복원으로 역할 구현을 대체하지 않는다.
- 서로 다른 소유 함수 충돌은 양쪽 구현을 보존해 해결하고 검사한다. 의미가 충돌하는 공통 계약은 해당 PR에 수정 요구를 남긴다. `ours/theirs`로 파일 전체 덮기, force push, 필수 검사 끄기는 금지한다.
- 후보에 모인 코드에서 남은 stub이 있으면 역할 PR에 정확한 단위를 요청한다. 문제를 분석해 해당 소유 역할로 수정 요청하고 수정된 head를 다시 merge한다. 작성자·실제 커밋 출처를 유지한다.
- **최종 게이트:** 미구현 0, missing/protected 불일치 0, harness·타입·빌드·백엔드·실제 API E2E·Compose 재시작·백업 복원 통과. `starter/templates/ci.yml`의 4개 acceptance job과 원격 필수 검사를 확인한다. 전체 서비스 Kiro 통합 완료는 이 결과가 있을 때만 선언한다.
- 1번 Kiro의 최종 head 검토와 GitHub의 필수 리뷰/검사가 충족되면 별도 일상 확인 질문 없이 최종 PR을 병합한다. `gh pr merge --admin` 같은 우회 옵션은 사용하지 않는다. base가 바뀌면 후보에 반영하고 영향 검사/검토를 다시 확인한다.
- 원격 base에 후보 커밋이 포함됐는지 확인한 뒤 역할 PR에 실제 포함 결과를 기록하고 닫는다. 이력 보존을 위해 역할 브랜치는 자동 삭제하지 않는다.

검사 실패를 무시한 부분 반영·임의 예외 승인은 하지 않는다. 외부 규정이나 GitHub 정책이 사람 승인을 요구하면 그 승인이 필요하다. 자동화 지시가 조직 정책보다 우선하지 않는다.

## 커밋·평가 기록 원칙

커밋 횟수를 평가한다는 것은 아직 추측이며 가산 기준을 만들지 않는다. 빈 커밋·한 줄씩 쪼개기·과거 작업 소급 생성·타인 author/날짜 변경·형식적 상호 승인으로 숫자를 늘리지 않는다. `feat(M04): ...`, `fix(M11): ...`, `test(M05): ...`처럼 실제 변경의 의미와 M을 기록한다. 하나의 단위에 실제 수정이 추가되면 그 이유의 커밋을 남긴다. 반입된 기반은 `chore: import permitted starter`로 출처와 범위를 밝히고 대회 중 작성한 코드와 구분한다.

PR당 단위 상태, 검사 결과, 실제 리뷰 지적과 후속 수정, 통합 PR을 남기면 과정이 추적된다. 목표는 진짜 구현·검증·협업 이력이며 정해진 커밋 개수 충족이 아니다.

## 팀원에게 줄 시작 프롬프트

역할 번호만 바꾼다. 설정 파일은 팀 공통으로 준비한다.

```text
너는 ZZIK의 3번 담당 Kiro다.
START_HERE.md, AGENTS.md, .zzik-assembly.json,
docs/hackathon/PR_WORKFLOW.md, starter/roles/03.md를 읽어.
assembly_plan.py plan과 preflight --role 3으로 환경을 확인하고
정해진 단위 순서·브랜치·교차 검토·통합 절차를 수행해.

일상적인 작업 선택·검사·커밋·push·PR·배정된 리뷰는 묻지 말고 진행해.
3번이면 후보 통합과 최종 검사·정책을 충족한 PR 병합까지 맡아.
다른 역할이면 자기 구현과 배정된 교차 검토를 완료하고
통합 피드백에 대응해. 원격 상태에서 재개하고 중복 PR을 만들지 마.
실제 변경·검사·AI 검토 기록만 남기고 커밋 개수를 꾸미지 마.
공식 저장소 규정·권한·인증이 없으면 그 외부 조건만 보고해.
새 AWS 자원 생성·실제 서버 중단·완성본 코드 복원은 하지 마.
```
