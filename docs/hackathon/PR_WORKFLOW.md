# Kiro 조립 연습: 작업·PR·병합 운영 규칙

이 규칙은 `starter/local-v1` 조립 연습에 적용한다. 원본 서비스의 누적 개발 PR은 각각 기존 의존 브랜치를 유지한다. 교육·대회 공식 규정은 별도 확인한다. 아래는 Kiro가 따라야 하는 작업 지침이며 GitHub branch protection이나 자동 승인 봇이 설치됐다는 의미는 아니다.

## 담당을 먼저 고정한다

- 각 역할 Kiro: 작업 선택 → 구현 → 검사 → 커밋 → Draft PR 생성/갱신 → 리뷰 준비 여부 판정까지 수행한다. 별도 지시 없는 병합·승인 대행은 하지 않는다.
- **3번 담당자를 조립 통합 담당으로 지정한다.** 병합 대기열과 공통 API/DB를 관리한다.
- 작성자 외 **사람 1명 이상**이 리뷰한다. 3번 본인 PR은 1번 담당이 최종 병합한다.
- 공통 UI 변경은 2번, API/DB는 3번, 인프라는 1번의 검토를 추가로 받는다. 작성자가 해당 담당이면 다른 사람이 리뷰한다.
- 실제 이름/계정은 팀에서 1~5번에 배정한다. Kiro는 계정을 추측해 리뷰를 요청하거나 팀 채팅을 전송하지 않는다. 저장소 push 권한이 없으면 로컬 커밋과 PR 본문 초안을 남기고 권한 부족을 보고한다.

## 한 번에 작업할 크기

첫 PR은 자기 `starter/roles/NN.md`의 **구현 단위 1개**로 제한한다. 이후에도 기본은 1개이며, 분리하면 실행/검사가 불가능한 긴밀한 의존 단위만 이유를 적어 묶는다. M 전체나 역할 전체가 끝날 때까지 기다리지 않는다. 문서 PR은 문서 변경 자체를 한 단위로 본다.

공유 파일의 함수 소유권과 `docs/hackathon/plan.json`의 선행 관계를 따른다. 프롬프트를 읽고 필요한 선행 함수/계약이 이미 제공되어 있는지 실제 코드로 확인한다. 다른 담당 구현이 없어도 독립 함수 테스트가 가능하면 진행하고, 없으면 자신의 다른 독립 단위를 선택한다. 작업이 없으면 의존성 대기로 보고한다. 다른 담당 코드를 임의로 완성하거나 성공 응답으로 위장하지 않는다.

## Kiro의 상태 판정과 행동

| 상태 | 판정 조건 | Kiro가 할 일 |
|---|---|---|
| 구현 중 | 단위가 미완성 | 같은 브랜치에서 계속 작업. 방향 검토가 필요하면 Draft PR |
| 검사 차단 | DB/도구/선행 구현이 없어 필요한 검사를 실행 못 함 | Draft PR에 차단 이유·담당·필요 기능/PR 기록. 독립 작업만 계속 |
| 수정 필요 | 이번 변경의 검사 실패, 계약 불일치, 원인 미상 실패, 소유권 위반 | Draft 유지하고 수정. 원인 미상을 타 역할 미구현 탓으로 단정하지 않음 |
| 리뷰 준비 | 아래 리뷰 준비 조건을 모두 충족 | 커밋·push 후 PR 생성/갱신, Draft 해제, `리뷰 준비`로 보고 |
| 병합 대기 | 사람 리뷰 또는 선행 PR 반영이 남음 | 자동 병합하지 않음. 의존 PR 변경에 따라 재검사 |
| 병합 완료 | GitHub에서 실제 merge 확인 | 최신 통합 브랜치를 반영하고 다음 단위로 진행 |

## 리뷰 준비 조건 — 모든 항목 필수

1. 선언한 단위의 함수/동작을 구현했다. `python3 scripts/starter.py status`로 **해당 단위**의 marker가 없어졌고 missing/protected 변경이 없는지 확인한다. 역할 전체 `check --role N`은 다른 단위가 남으면 실패할 수 있으므로 첫 단위 완료의 유일한 기준으로 삼지 않는다.
2. `.venv/bin/python scripts/check_harness.py` 통과. 프론트 변경 시 생성 타입 검사와 빌드도 통과한다. 문서만 변경하면 문서·프롬프트·경로 검사를 실행한다.
3. 기존 테스트에서 단위와 관련된 정상/실패 동작을 검사했다. 단위만 분리해서 검사하려면 실제 기존 테스트 ID와 선택 이유를 기록한다. 적합한 검사가 없으면 동작 테스트를 추가한다. marker만 지우거나 테스트를 약화하지 않는다.
4. 검사 명령·종료 결과·실패 원인을 PR에 기록한다. 실행 못 한 검사를 통과했다고 적지 않는다. 새 코드 회귀와 기존 미구현 실패를 구분할 수 없으면 Draft 유지.
5. `git diff --check`, 변경 범위·비밀정보·불필요 파일 확인. 선언하지 않은 다른 역할 구현을 변경하지 않는다. 계약/DB 변경이 필요하면 별도 의존 PR로 조율한다.
6. PR base는 `starter/local-v1`. M 번호·단위 ID·역할·선행 PR·공통 계약 변경·검사·미완료 사항을 작성한다. 같은 작업은 기존 PR을 갱신하며 중복 생성하지 않는다.

## 병합 판정 — 통합 담당자의 책임

일반적으로 사람 리뷰 1명 이상, 필요한 담당자 검토, 선행 구현 확보, 충돌 해결, 필요한 검사 통과 후 병합한다. Draft·원인 미상 실패·미검증 자기 기능·미해결 리뷰는 병합하지 않는다. GitHub의 실제 필수 검사/리뷰 정책은 우회하지 않는다. Kiro의 자기평가를 사람 승인으로 세지 않는다.

초기 all 프로필은 다른 역할의 빈 구현 때문에 전체 acceptance가 실패할 수 있다. **빨간 CI를 무시하라는 뜻이 아니다.** 부분 통합이 필요하면 통합 담당자가 다음을 확인하고 PR에 명시적으로 기록한 경우만 병합한다.

- 실패한 job/테스트와 남은 단위 ID의 대응이 설명되어 있다. 이번 변경의 회귀가 아니라는 비교 근거가 있다.
- 이번 단위의 실제 동작 검사와 계약 검사, 영향받는 빌드는 통과했다.
- 남은 단위의 담당/의존 작업과 통합 후 실행할 전체 검사가 명시됐다.
- 작성자 외 리뷰가 완료됐고 저장소의 필수 검사 정책상 병합 가능하다. 불가능하면 검사를 끄지 말고 선행 작업과 함께 검증할 통합 PR을 준비한다.

이 예외 판단은 Kiro가 자동 승인하지 않는다. 모든 단위를 합친 최종 상태에서는 **미구현 0, 전체 계약·백엔드·프론트·실제 서버 E2E·Compose/복구 CI 통과**가 필요하다. 로컬 완료와 AWS 3-Tier 배포 완료를 구분한다.

## 합쳐진 변경을 내 브랜치에 반영

작업 시작 전, 선행 PR이 병합됐을 때, 리뷰 요청 직전에 최신 통합 브랜치를 확인한다. `git status`로 자기 변경을 확인하고 완료한 작업만 먼저 커밋한다. 타인의 변경을 자동 커밋하거나 `reset --hard`, 강제 push로 덮지 않는다.

자기 작업 브랜치에서:

```sh
git fetch origin
git merge origin/starter/local-v1
```

충돌이 자기 소유 함수 안에서 명확히 해결 가능하면 수정하고 관련 검사를 재실행한다. 공유 계약·타 역할 코드의 의미가 충돌하면 해당 담당에게 필요한 결정을 보고한다. `ours/theirs`로 파일 전체를 덮지 않는다. 병합 후 달라진 의존성에 맞는 검사만 다시 실행하고 PR 결과를 갱신한다.

## 팀원이 Kiro에 처음 넣을 프롬프트

아래의 3/03을 자기 번호로 바꾼다.

```text
너는 찍(ZZIK)의 3번 담당이다.
START_HERE.md, AGENTS.md, starter/roles/03.md,
docs/hackathon/PR_WORKFLOW.md와 연결된 역할/M 프롬프트를 읽어.

이 운영 규칙을 따라 내 소유의 실행 가능한 단위 하나를 선택하고,
구현·검사·커밋·push·Draft PR 생성/갱신까지 진행해.
리뷰 준비 조건을 충족하면 Draft를 해제하고 결과를 알려줘.
PR base는 starter/local-v1이다. 승인이나 merge는 하지 마.
선행 작업 때문에 막히면 필요한 단위/담당/PR을 기록하고
다른 독립 작업이 있으면 계속 진행해.
완성본 복사와 기준 구현 복원, 새 AWS 자원 생성은 하지 마.
```
