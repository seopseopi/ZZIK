# 찍 · 서비스 완성과 대회용 작업 기반

작성 기준: 2026-09-17, 출발점은 `main`의 초기 구현 커밋 `d06ca14`. 팀원 새 원문을 반영한 실행 계획은 [해커톤 가이드](hackathon/README.md)가 우선한다.

이 문서에서 하네스는 **각 기능을 독립적으로 구현·교체하고, 정해진 입력·출력과 테스트로 다시 통합할 수 있는 코드·실행 환경·작업 명세 묶음**을 뜻한다. 아래 항목은 후속 작업 계획이며 완료 보고가 아니다.

## 현재 위치

- 프론트·FastAPI·PostgreSQL·파일 저장·분석 worker·보정·승인 핵심 흐름을 구현했고 로컬에서 검증했다.
- 앱 분석 함수는 합성 사진으로 실제 Rekognition 호출 6회를 검증했다. S3·EC2 역할·API/worker/DB 종단 연결과 실사진 품질 검증은 남아 있다. [검증 범위](AI_VALIDATION.md).
- 공개 GitHub Pages는 브라우저 체험판이다. 원격 서버·DB 기반 다중 사용자 서비스와 구분한다.
- GitHub CI는 백엔드 테스트·프론트 빌드·체험판 E2E를 실행한다. 이번 1단계에서 실제 API·worker·독립 DB를 함께 구동하는 E2E 실행기와 CI 작업을 추가했다. 실행 결과는 [검증 상태](IMPLEMENTATION_STATUS.md)에 기록한다.
- 초기 커밋은 보존한다. 이번 1단계에서 역할 5개·M 작업 17개·공통 계약·PR 규칙을 추가했으며 이후 변경부터 실제 기능 단위 이력을 남긴다.

## 2. 완성본을 다시 조립할 수 있게 정리

완성 전부터 기능 경계와 테스트를 정리한다. 완성본에서 코드를 한꺼번에 삭제하며 분해하면 통합 기준을 잃기 쉽다. 검증된 전체 구현을 기준본으로 보존하고, 별도 starter에서 구현 경계·샘플·검증기를 제공한다.

### 기능 경계 제안

| 모듈 | 책임 | 반드시 맞춰야 할 계약 |
| --- | --- | --- |
| 계정·앨범 | 세션, 멤버십, 초대, 앨범 관리 | 사용자/앨범 ID, 역할, 접근권한·오류 형식 |
| 업로드·저장·작업 | 파일 검증, 저장, 분석 작업 생성·재시도 | 원본 키·해시, 요청 ID, 작업 상태·정리 책임 |
| 인물·검색·추천 | 분석 제공자, 인물 수정, 태그·그룹·검색 | 얼굴/인물 대응, 확정·미확정·실패, 수동 수정 보존 |
| 보정·버전 | 렌더링, 비교, 버전 분기, 다운로드 | 원본 보존, 설정·렌더러 버전, 부모 버전·출력 규칙 |
| 승인·협업 | 승인 대상, 승인·취소, 최종본, 댓글·보드 | 불변 승인 대상, 전원 합의, 재검토·최종 해제 |

위 표는 코드의 기능 경계다. 실제 5명 배정은 새 원문의 인프라/프론트/백엔드/AI/보정으로 확정했으며 [담당 경계](hackathon/OWNERSHIP.md)를 따른다. DB 모델·마이그레이션·공통 응답 타입은 공동 변경 규칙과 통합 담당을 둔다.

### 준비할 산출물

- `AGENTS.md`: 실행 명령, 코딩 규칙, 손대면 안 되는 공통 계약, 변경 후 필요한 검사.
- `contracts/`: API 요청·응답 스냅샷, Python 매개변수 검사, OpenAPI 기반 프론트 타입 생성·일치 검사 추가. 상세한 예제·상태 전이 문서 확대는 후속 작업.
- `docs/hackathon/tasks/`: 기능별 목적, 선행 작업, 담당 파일, 인터페이스, 완료 조건, 검증 명령 추가.
- `fixtures/` 또는 기존 fixture 정리: 같은 샘플로 같은 결과를 재현하고 정상·실패·미확정 케이스를 구분.
- 통합 실행/초기화 명령: 개발 데이터와 테스트 데이터를 분리하며 초기화 대상을 명시.
- 테스트 묶음: 모듈별 검사 + 계약 검사 + 실제 API·worker·DB 기반 전체 시나리오.
- 기준본과 starter 사용법: 기준본 참조 위치, 각 작업을 넣는 순서, 통합 실패 시 복구 방법.

2단계에서 `backend/app/main.py`의 API를 도메인별 라우터/공통 처리로, `frontend/src/App.tsx`의 화면을 기능별 컴포넌트로 분리했다. 실제 경로는 [모듈 지도](hackathon/MODULES.md)를 따른다. 동작을 바꾸는 기능 추가와 구조 분리를 별도 PR로 관리한다.

## 3. Git과 CI

1. 현재 구현을 출발점으로 보존하고, 전체 서비스 검증 후 별도 기준 태그를 남긴다. 태그명은 실제 완료 단계에 맞춘다.
2. 앞으로의 변경은 `feat/기능명`, `fix/문제명`, `refactor/모듈명` 브랜치에서 기능 단위 PR로 기록한다. 기존 초기 커밋을 팀원별 개발 이력처럼 재작성하지 않는다.
3. PR 양식은 해결할 문제, 변경 동작, 검증 결과, DB/API 변경 여부를 포함한다. 이슈에는 담당자와 완료 조건을 둔다.
4. `main`에 필수 CI와 리뷰 규칙을 설정하고, 인원에 맞는 `CODEOWNERS`를 작성한다. 아직 팀원 GitHub ID·역할은 정해지지 않았다.
5. 1단계에서 CI에 실제 서버용 E2E 3개를 추가했다. PostgreSQL·API·worker를 띄우고 독립 계정으로 업로드부터 최종본 취소까지 검증한다.
6. DB 마이그레이션·공통 계약 변경을 검사한다. 체험판 검사만 성공했다고 실제 서비스 통합 검증이 끝난 것으로 취급하지 않는다.
7. 공유 체험판 배포와 실제 서버 배포를 분리하고, 각각 어떤 커밋이 배포됐는지 기록한다.

대회 사전 준비물·기존 코드 사용 허용 범위를 확인한 뒤 기준본·starter의 대회 사용 범위를 정한다. 준비한 코드와 대회 중 실제 변경의 이력은 구분해서 남긴다.

## 권장 진행 순서

1. 현재 검증을 기준으로 도메인 경계·API 계약·작업 문서 정리.
2. Docker 전체 실행·재시작과 실제 서버 E2E의 CI 편입(2단계에서 검사 추가; 결과는 PR Checks에 기록).
3. 실제 S3·Rekognition 연결, 실사진·원격 다중 사용자 검증.
4. 장애 복구·처리량 측정 후 전체 서비스 기준 태그 확정.
5. 기준본을 보존한 채 starter와 기능별 작업 묶음을 만들고, 각 작업을 다시 통합해 전체 테스트 통과 확인.

이 단계의 완료는 파일을 나누는 데 그치지 않는다. **팀원이 자기 작업 명세만 보고 기능을 완성하고, PR을 통해 합친 결과가 동일한 전체 서비스 검증을 통과하는 것**이 목표다.
