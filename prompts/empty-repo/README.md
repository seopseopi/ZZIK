# 빈 저장소에서 시작하는 찍 / ZZIK 연습

**정정: 대회 출발점은 빈 저장소다.** `starter/local-v1`은 이미 인증·스키마·계약·디자인·테스트가 제공되는 부분 구현 연습이므로 이번 대회 모의 연습의 출발점으로 사용하지 않는다. `.starter-state.json`, `starter.py`, `assembly_plan.py`, 기존 30개 stub, 기존 테스트 통과 기록도 새 저장소의 전제나 완료 증거가 아니다.

이 폴더는 사람이 각 개발 에이전트에 전달하는 **자연어 지시문 묶음**이다. 구현 코드·DB 스키마·OpenAPI·테스트·이미지·Docker 설정을 포함하지 않는다. 새 저장소에 기존 ZZIK 소스나 생성물을 복사·clone·cherry-pick·archive·검색해서 답안으로 가져오지 않는다. 기존 저장소를 원격으로 등록하지 않는다. 공식 문서와 공개 라이브러리는 대회가 허용한 범위에서 사용한다. 프롬프트 자체의 반입 허용 여부도 실제 규정을 따른다.

## 팀이 준비할 사실

제공 저장소 OWNER/REPO, 실제 제출 브랜치, 1~5번 GitHub 계정, 실행 ID, 사용 가능한 AI/네트워크/프롬프트 반입 범위를 한 번 정한다. 비밀번호/토큰은 각자 로그인하고 공유하지 않는다. AWS 자원 생성은 현재 보류다. 대회 계정·예산·배포 승인이 별도로 생기기 전에는 로컬 검증만 수행한다.

연습 때에도 기존 starter를 가져오지 않고 팀 소유의 **새 빈 연습 저장소**를 사용한다. 실제 대회에는 주최 측 저장소를 사용한다. 이 문서 작성 과정에서는 새 저장소나 AWS 자원을 만들지 않았다.

## 시간 순서 — 처음부터 전원이 구현을 시작하지 않는다

| 단계 | 실행 담당 | 결과 / 다음 시작 조건 |
|---|---|---|
| G0 저장소 시작 | 1번, 검토 3번 | 실제 계정/원격 확인, 프로젝트 설명·팀 설정·소유권·Git 규칙을 새로 작성. 출발 커밋 확보 |
| G1 공통 기반 | 3번, 검토 1번; 1번은 개발 환경 지원 | DB 설계·마이그레이션·인증·계약·분석/보정 인터페이스·기본 동작 테스트를 새로 구현. 합의된 계약과 실제 기반 검사 통과 |
| G2 역할별 구현 | 1~5번 병행 | 2번 화면, 3번 API/작업 처리, 4번 분석, 5번 보정/승인, 1번 실제 실행 스택. 역할별 검사·Git 이력 생성 |
| G3 통합 | 3번, 최종 검토 1번 | 후보 브랜치에서 1→3→4→5→2 역할 커밋 통합, 실제 다중 계정 E2E·재시작·백업 복구, 전체 CI 통과 후 제출 브랜치 반영 |
| G4 3-Tier 실배포 | 별도 승인/환경 확정 후 1번 주관 | Web/App/RDS 분리 배포, 비공개 S3, App 장애·복구 검증. 로컬 완료와 별도 기록 |

2·4·5번은 G0/G1 동안 프롬프트 이해·도구 설치·계약 검토는 할 수 있지만 각자 다른 DB/API 계약을 구현하지 않는다. 입력·출력 계약이 확정된 독립 기능부터 병행한다. 세션 시작/재개는 사람이 실행하며 항상 원격 상태를 먼저 읽는다. 다섯 에이전트가 자동 기동되는 서비스는 없다.
